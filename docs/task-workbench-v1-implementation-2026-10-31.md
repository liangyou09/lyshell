## 使用入口与首发范围

右侧任务区 **Sessions → 任务工作台 → 新建**。先保存目标，再点击“创建并排队”；再次运行创建新的 Submission。打开页面、切换历史和编辑草稿均不会提交执行。

本次接入持久等待、受控并发、人工介入、未知交接核对、成果快照与验收。复用原生 Harness 的模型执行、task/attempt、审批、停止与恢复，不增加第二套 Agent 循环。

- 采用 **H 路线：宿主持久待提交队列**。控制范围仅为本工作台登记的执行。
- 默认并发 2，可配置 1—8；等待上限 100。普通任务 FIFO，资源冲突时允许后续独立任务前进，续接重新排到队尾。
- 新进程启动后暂停新派发。恢复队列不会自动 recover、resume、批准旧审批或重发未知提交。
- 独占资源由用户明确登记稳定 ID；原生终态只归还执行槽位，资源须保存人工核对依据后释放。网络断开、取消请求和任务卡片导航均不会解除占用。
- 首发包含通用目标及“组件性能 · 分析已有结果”。性能模板使用冻结的用户数据计算差异，再交由 Harness 分析；**未开放受管测试脚本执行模式**。

## 用户补充的审批要求

新建任务的审批策略默认 **全部默认通过**，也可选择“逐项人工审批”。策略固定到每次运行，编辑草稿只影响后续运行。

自动允许只覆盖当前进程明确派发的、属于工作台专有 scope 的新执行。每个请求仍经过现有 `approveWorkbenchActivity`：fresh read、后台/会话/任务/审批 ID/真实选项以及完整工具参数检查。只回答实际提供的 `allowed-once`，不改变后台 sandbox、operating mode 或其他调用方权限。

审批意图先持久记录，回执未知时不自动重复允许。应用重启后旧执行转人工核对；无完整操作参数或身份不符时仍不能自动允许。审批观察异常不会把已经确认的原生绑定改回未提交。

## W00 能力判断与唯一队列路线

实际安装的官方 dsh：**0.2.1-rc.2**，由 `dsh --version` 与已安装包版本交叉核对。现有宿主桥使用 native-work v2；原生工作通道实测返回 `durability: durable`。

| 核实项 | 证据与本次决定 |
| --- | --- |
| C01 超量提交 | 公开原生接口同会话返回 busy；不同会话可以并行。既有原生并发回归通过，隔离真实执行观察到两个不同任务同时 running。 |
| C02 等待项定位 | 当前公开原生请求没有业务等待项的独立 queueId/查询/撤回协议。H 路线使用持久 Submission ID。 |
| C03 等待持久性 | 不宣称上游内部 prompt 队列已具备本方案所需耐久性。H 路线真实磁盘测试与独立新进程加载保留等待项。 |
| C04 撤回与暂停 | H 路线 waiting 原子撤回，不调用 Harness；暂停在会话准备后再次核对，禁止继续 submit。 |
| C05 并发范围 | 原生为每会话一个活动任务；本层另控制自身 scope 的 slotHeld，上限默认 2。审批、取消未确认和交接未知继续占槽。 |
| C06 回执丢失 | 有专属会话时只读核对原 requestId/task/attempt；new 未知且无确切 sessionId 时保持隔离，不按目录猜测归属。 |
| C07 重启派发 | 新进程实测暂停队列，等待和未知占用仍在，零原生调用、不启动后台。 |
| C08 业务资源 | 未确认上游提供本方案的稳定 resourceId 准入；本层持久保存独占资源，并与领取/提交意图同一清单原子写入。 |

没有向原生协议添加猜测中的队列参数，没有在故障时切换路线。上游内部队列的持久、暂停和资源规则仍属于未核实能力，不能据此宣传全后台限流。

## 实现边界

共享业务契约位于 `src/shared/task-workbench.ts`，严格公开 DTO 校验位于 `task-workbench-validation.ts`。主进程 `src/main/task-workbench/` 分担业务仓储、队列、原生适配、成果与 IPC；渲染层只有业务摘要 store 和现有 Sessions 内容中的详情组件。

工作台使用 `userData/task-workbench/scope-id` 派生专有 owner，与 global/session/Pet/Web scope 分开。owner、凭据和桥地址不进入 renderer。损坏 scope 不重新生成身份接管旧会话。

`manifest.json` 使用现有异步原子文件基础：单写者、串行事务、写后发布、操作 ID 与参数指纹去重、草稿 revision 检查。清单上限 2 MiB，操作回执最多 10000，不淘汰去重依据；写失败先核对磁盘，结果不确定时锁定，不用旧内存覆盖可能已提交的记录。Windows 不承诺完整机器掉电耐久性。

冻结输入先保存为受管文件，再登记引用。排队运行固定目标修订、输入摘要与目录身份；同路径目录被替换后拒绝派发。结果使用新的文件版本与 SHA-256，单文件 5 MiB、单次总量 20 MiB，拒绝越界、junction/符号链接、变化中的文件、非法 UTF-8 和摘要不符。公开读取及导出只接受 artifactId。

执行、观察与验收分别保存。原生完成不自动代表目标完成；自定义完成条件需要人工确认，人工确认不能覆盖文件损坏、执行关联错误或其他硬检查失败。性能回退与验收结论独立：报告可以合格且发现回退。

业务观察复用既有活动刷新节拍，不添加另一套定时轮询。精确补查单次最多四个并发，优先核对占用。应用开始退出时同步关闭派发 gate，已有收尾使用原生命周期总预算。

## 提交前代码复审（2026-10-31）

本轮由 Codex 亲自审查全部实现与修改，并修复以下可操作问题：

- 续接沿用同一 Submission 和冻结输入，旧报告可能被当作新 attempt 成果。现在持久保存当前 `executionRequestId`，初次提交及续接提示均要求报告写入对应 `Execution-Request` 标记；旧报告不能通过新执行的验收。
- 会话准备期间降低并发上限，原已领取的等待项仍可能越过新额度提交。现在发送前重新检查额度，未提交的项回到等待并保留已确认会话。
- 观察先确认续接、原始续接回执后返回时，重复绑定可能错误标记交接未知。现在按同一执行请求幂等绑定，只保留一条旧 attempt 历史。
- 已完成任务不再周期读取，稍后验收可能只拿到过期完成证据。采集前会精确读取当前原生执行，再使用新鲜证据验收。
- 会话准备期间同路径工作目录被替换，原先缺少实际 submit 前的目录身份复查。现已在会话准备后复查，失败时不发送执行。
- 性能输入的环境字段长度与确定性比较器不一致，且大小写变体重复指标可到验收时才失败。现已对齐长度，并在保存入口拒绝归一化后的重复指标。
- 操作回执未确认后，后续读取成功可清掉错误文本，使界面保留 pending 锁定却隐藏核对按钮。现在 pending 本身也保持核对入口可见，重试仍使用原操作 ID；新增界面回归 **1 文件、2 项通过**。

两个主要问题均先用测试复现：原实现将旧报告判为 `passed`，且降低额度后第二项仍为 `bound`。修复后补充了相应故障和交接时序用例。最终业务、IPC 与生命周期回归 **17 文件、194 项通过**；既有原生与侧栏回归 **8 文件、151 项通过、2 项既有跳过**。真实磁盘、junction 与原子重命名验证使用正常本地权限；沙箱中的权限失败原始日志保留，没有修改断言绕过失败。日志位于本 checkout 的 `tmp/goal-review/`。
