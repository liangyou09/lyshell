- 日期：2026-10-23
- 状态：P0-A 最小闭环已实施并验收（边界与未验证项见下）；后续阶段待实施
- 范围：产品定位、核心工作流程、功能改进顺序与名称决策
- 当前建议：保留 LyShell 名称，优先完善项目恢复和运行状态体验

## 1. 产品定位与目标用户

产品定位为：**以项目为中心的 AI 开发工作台。**

对外可先采用以下表达：

> **LyShell — 面向 AI 开发的终端工作台**
>
> 统一组织项目、Agent 和终端。

首批目标用户为在 Windows 上使用命令行 AI Agent，同时需要自行运行、调试和部署项目的个人开发者与小团队开发者。

核心工作流程为：

> 打开项目 → 选择并启动 Agent → 运行命令与验证 → 查看结果 → 下次继续工作。

产品改进围绕这条流程展开。SSH、SFTP、串口、插件和脚本能力继续作为连接与扩展能力，不必全部放在首次介绍的同一层级。

## 4. 分阶段实施计划

### 阶段一：项目现场恢复与继续工作（P0-A）

**目标：** 用户第二次打开项目时，不必重新寻找和组织全部工作入口。

实施内容：

1. 明确项目身份与目录预设的关系，复用现有规范化目录和 worktree 身份，避免另建一套冲突的项目配置。
2. 定义带版本号的项目现场数据，记录恢复所需的目录引用、Agent 启动项引用、可恢复文档／网页入口、标签顺序和分屏布局。
3. 增加“保存项目现场”“继续上次工作”入口，并明确自动保存与手动保存的边界。
4. 先恢复资源入口与布局；文档和网页按可重新打开的入口恢复，不承诺恢复编辑状态、表单内容或完整浏览器运行状态。
5. 对 CLI 会话续接分别核实支持方式。支持时提供明确入口；不支持时保留普通启动能力并说明边界。
6. 将“恢复界面”“重新启动进程”“续接 Agent 对话”区分展示，不自动重跑上次命令或重复提交任务。

持久化只保存必要引用与允许恢复的资源入口，不保存密钥或一次性认证地址；网页恢复需排除携带敏感认证信息的地址。

验收标准：

- 退出并重开应用后，可以恢复一个项目的约定资源入口和布局。
- 两个项目及其不同 worktree 的现场不会串用。
- 目录移动、文件删除、预设删除或 CLI 不可用时，显示具体失效项，并允许恢复其余有效资源。
- 用户可选择保存的现场，不会因恢复操作自动执行测试、部署或其他历史命令。
- 界面不将已退出的进程显示为仍在运行，不将新对话显示为已续接旧对话。

### 阶段二：会话／任务状态与提醒（P0-B）

**目标：** 用户能找到需要处理的工作，且不会被不可靠的“运行中／已完成”误导。

实施内容：

1. 分开建模进程状态、任务状态与连接状态；进程存活不能直接推导为任务正在执行。
2. 优先接入原生 Harness 已提供的权威状态；其他 CLI 通过明确的适配能力逐步接入。
3. 显示状态来源与新鲜度。无可靠来源、连接中断或后台身份改变时，展示未知或过期状态。
4. 提供项目范围内的会话列表，支持跳转到相应终端或工作页面。
5. 针对可靠识别的等待输入、等待审批、失败和完成事件提供提醒，并支持静音与去重。
6. 审批入口展示实际操作与后端提供的选项，由用户决定，不自动批准。

验收标准：

- 同一项目多个会话并行时，用户可以定位到对应会话。
- 工具支持时能准确展示任务状态；不支持时明确显示未知，不用终端文字猜测结果。
- 连接中断、超时和后台重启不会被解释为任务完成，也不会触发自动重发。
- 终态、审批和提醒均关联正确的后台实例、会话与任务。
- 同一事件不会因轮询反复提醒；切换项目后仍能定位提醒所属项目。

### 阶段三：项目常用操作（P1-A）

**目标：** 减少目录切换与重复输入，让常用命令在正确的上下文中执行。

实施内容：

1. 优先复用现有快捷命令，支持项目常用操作的组织与入口。
2. 允许用户保存开发、测试、构建等命令，并明确其目录、worktree 和环境来源。
3. 执行前展示命令与目标，执行后可跳转输出；结束时保留可核实的退出结果。
4. 同一操作正在运行时，提示用户已有执行，避免误点击造成重复启动。

验收标准：

- 同一操作在项目主目录和专属 worktree 中执行时，目标正确且可见。
- 失败后可查看实际输出；重试由用户触发。
- 项目恢复不会自动执行这些操作。

### 阶段四：启动配置可解释（P1-B）

**目标：** 用户能够回答“这次到底用什么配置、在哪个目录启动”。

实施内容：

1. 增加最终生效配置摘要，包括目录、worktree、Agent 命令、模型、环境变量组来源及权限。
2. 区分显式配置、跟随配置和 CLI 默认值；无法确定的值不伪装成已确认值。
3. 敏感字段默认隐藏；摘要、日志与导出不泄露凭据。
4. 对依赖缺失、目录失效、worktree 准备失败等错误，提供具体说明和对应处理入口。

验收标准：

- 摘要与实际启动参数、目录和环境来源一致。
- 切换变量组或修改预设后，摘要按约定更新，不残留旧值。
- 错误提示足以定位失败环节，且不会把部分准备成功报告为启动成功。

### 阶段五：工作结果查看（P1-C）

**目标：** 用户能够判断本轮工作做了什么、验证到了哪一步。

实施内容：

1. 提供项目／worktree 的 Git 状态与变更查看入口，优先解决查看和跳转。
2. 将执行记录、终端输出和验证结果关联到对应项目、目录与会话。
3. 明确区分 Agent 自述完成、进程退出和实际验证通过。
4. 结果查看的最小版本不承担完整代码编辑器或自动合并系统的范围。

验收标准：

- 可以从结果入口定位实际变更、执行目录和输出。
- 未运行、失败或过期的验证结果不会显示为当前已通过。
- 查看结果不会隐式提交、覆盖或合并用户修改。

## 5. 实施方式与验证要求

- 主进程负责文件、进程、CLI 适配与持久化；Renderer 负责展示和用户操作，经 preload 桥访问能力。
- 新增 IPC 时同步更新 handler、validator、preload 和消费端 store／hook，并补齐共享类型。
- 实施前核实涉及模块的当前行为，保留现有项目预设、终端与连接能力，避免为新入口重建重复配置体系。
- 将数据模型、资源恢复和状态归一化等纯逻辑与 IO 分离，优先测试可独立验证的规则。
- 每阶段由 Codex 亲自检查代码与集成结果；实际图形界面检查不能由文本工作助手替代。
- 每阶段交付说明需列出改动、验证结果、恢复范围、CLI 支持范围与未覆盖场景。

每阶段至少完成一次真实流程验证：创建／选择项目 → 启动 Agent → 运行验证 → 查看结果 → 退出重开。针对该阶段增加目录失效、进程退出、连接中断等必要失败场景。

当前尚无用户行为基线。先记录找回工作入口所需步骤、首次启动失败原因和配置理解问题，再决定是否设定量化指标，不预先承诺未经测量的效率提升。

## 6. 名称与品牌决策

### 当前建议

保留 **LyShell**，先使用“面向 AI 开发的终端工作台”作为定位说明。

原因：

- 终端仍是承载开发工作的核心能力，Shell 与现有产品不冲突。
- 当前更重要的工作是完善恢复、状态和结果查看体验。
- 名称已经用于安装包、命令入口、配置与 MCP 接口；整体替换需要兼容与迁移设计。

暂不采用 **Fly Launcher** 作为总品牌。Launcher 更适合启动入口，覆盖持续工作、结果检查和再次继续工作的表达较弱。

### 何时重新评估更名

完成 P0 后，结合以下证据重新评估：

1. 目标用户是否持续因 LyShell 名称误解产品用途，且副标题无法有效改善。
2. 用户是否主要围绕项目与 Agent 工作，而终端已更多成为工作台的底层能力。
3. 新名称是否能带来更清楚的理解与更好的记忆，而非仅有主观的新鲜感。
4. 候选名称的公开使用、域名、软件分发及必要商标核验是否完成。

更名不是完成上述功能后的自动动作，应另行形成候选比较与迁移方案。

### 若决定更名的迁移原则

- 区分对外显示名称和内部技术标识，避免一次性全量替换。
- 评估安装升级身份、用户数据目录、资源管理器入口、命令别名、协议链接、MCP 工具和插件 API 的兼容。
- 优先保留旧入口或提供明确迁移，验证原有安装能够升级并读取原数据。
- 在迁移完成前，不将新品牌发布视为仅替换图标与文案的任务。
