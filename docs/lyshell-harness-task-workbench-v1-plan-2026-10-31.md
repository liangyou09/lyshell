- 状态：实施设计，尚未实施本文新增功能，尚未执行本文新增验收。
- 代码基线：795b6eccd1bb61429c2614402044efb6602a674f。本次只读核对远端 main 仍指向该提交；未同步的本地修改不在本次证据范围内。[R01]
- 文档定位：替代上一版“先建设完整 Agent 任务运行时”的实施建议。本文独立包含目标、复用边界、能力核实、接口、数据、实施工单、验收与发布要求，不需要同时执行旧方案。

## 0. 先确定正确的建设范围

### 0.1 本次修正

上一版把“现有能力”“接入现有能力的工程工作”和“可选的业务增量”混成了一个大型运行时工程。当前 LyShell 已经拥有原生任务、执行尝试、持久请求、去重、审批、多会话并发和恢复协议，继续复制这些能力会形成两份状态和两套控制逻辑。[R02][R03][R04]

修订后，第一版按以下方式建设：

1. 核对实际安装的 Harness 与桥接版本，确认可调用的能力。
2. 使用现有主进程服务和活动视图管理原生执行。
3. 保存用户目标、冻结输入、原生执行引用、成果和验收结论。
4. 排队只选择一条实现路线：接通原生队列，或补充宿主的待提交队列。
5. 只有明确的业务资源约束未被后端覆盖时，才补充有限的派发规则。
6. 保留提交关联、未知结果核对等必要正确性要求。

“轻量”指新增职责少、权威来源清楚，不意味着把应当持久保存的状态留在内存中。

### 0.2 用户要求的五项目标仍然保留

| 目标 | 第一版完成条件 | 优先实现方式 |
| --- | --- | --- |
| 任务排队 | 超出可运行数量的任务能等待、查询、取消，等待记录可按产品约定恢复 | 已验证的原生队列；否则宿主待提交队列 |
| 受控并发 | 明确控制范围和上限；等待审批、交接未知不会错误释放额度 | 原生并发机制，加确有必要的派发限制 |
| 人工介入 | 当前审批、停止请求、人工说明、核对与合格续接能完成 | 原生控制入口加现有工作台交互 |
| 故障核对 | 回执丢失、断线、重启后能找回关联，未知时不重复执行 | 原生记录与查询，加宿主交接记录 |
| 结果验收 | 结果对应正确输入和执行；能区分执行结束、验收结论与业务异常 | 模板检查工具、成果索引和人工确认 |

只有任务卡片、执行状态和审批界面时，可以交付“工作台预览版”；尚不能宣称上述五项目标全部完成。

### 0.3 事实与设计的标记

- **已存在**：本次代码基线或仓库协议中可以定位的能力。
- **待验证**：尚未在实际后端上完成行为核实，不能根据名称推断。
- **新增设计**：本方案要求增加的业务行为。
- **条件实施**：只有能力核实证明缺失时才实施。
- **建议默认值**：起步配置，需要实测，不是现有性能数据。

文档中的文件路径和接口分为“现有”与“建议新增”。示例类型和伪代码用于界定契约，未展示的基础类型和具体函数仍需要实现。

## 1. 当前已有能力：先复用，再找缺口

这里的“现有 Harness 链路”包含官方 DeepSeek Harness、LyShell 原生桥和宿主集成。不能把桥已经完成的工作忽略，也不能把所有桥能力都归为上游 Harness 原生功能。

### 1.1 能力清单

| 能力 | 基线中的证据 | 本版处理 |
| --- | --- | --- |
| 模型推理、工具执行和原生权限策略 | 官方 dsh 执行，LyShell 原生入口转发 [R02][R07] | 复用 |
| 多会话并行 | 同一凭据不同会话可同时执行，每会话最多一个活动任务 [R02][R04] | 复用；额外额度按实际需求决定 |

| 有界退出 | 应用生命周期分阶段处理 [R16] | 接入，不另建退出系统 |

### 1.2 不能把“接口没有暴露”当成“后端不会”

基线桥调用 controller().prompt 时已经使用 mode: 'queue'，但同一会话存在活动任务时，当前工作接口会先拒绝为 task/busy。[R04]

这个事实只能证明底层存在队列相关调用语义，不能证明：

- 等待项已经持久化；
- 等待项具有独立、可查询、可取消的身份；
- 跨会话有业务所需的全局并发额度；
- 队列能在重启后保持暂停；
- 主机或工作目录能够按业务资源规则互斥。

也不能直接移除 busy 检查来“开启排队”：当前任务映射、回合关联、审批和取消都依赖现有会话活动边界。先验证官方行为，再决定是否扩展原生桥。

### 1.3 保留现有约束

- 执行事实以对应原生任务和 attempt 的证据为准。
- 离线快照用于恢复上下文，不冒充当前执行证据。
- 读取状态、打开页面、归档和激活都不启动或重放工作。
- 取消请求已发送，不等于执行已经停止。
- 人工审批必须使用当前真实请求，不自动批准。
- owner、桥 key 和凭据始终留在宿主可信范围内。
- 无权接管 Pet、Web 或其他调用方的会话。
- 保留终端输入控制、既有连接方式、IME 和 renderer 隔离。
- 实施者亲自审查源码；本方案没有调用运行中的用户后端，也没有执行真实后端验证。

仓库的概述性文档可能保留旧版本描述；能力判断应核对具体实现、当前工作协议和实际响应。仓库对权限、审查和用户确认的要求仍然适用。

## 2. 第一版产品定义与支持边界

### 2.1 产品定义

用户从现有项目、目录、终端或连接创建业务任务，选择目标和完成条件。LyShell 将这份业务信息与一次原生 Harness 执行关联。任务在选定队列中等待和执行，用户在现有工作台处理审批与异常，最后查看成果和验收结论。

第一版新增的主要价值是：

- 明确“为什么运行”和“使用哪些输入”；
- 把执行与现有项目、主机和成果关联；
- 管理多个任务的等待与产品规则；
- 记录可查看、可复验的交付结果。

### 2.2 明确控制范围

默认只承诺控制**本任务工作台发起并登记的工作**。

其他 MCP 客户端、用户独立打开的 Harness 会话、Pet 和手工运行的进程，不会自动受到这层业务额度约束。要把范围扩大到整个后台，必须让所有相关入口经过同一个实际执行规则，并完成相应测试。

同一资源的互斥也只覆盖已经登记的资源关系。例如两个连接配置都指向测试环境 A，应配置同一个稳定 resourceId。不能仅凭不同连接名称就判断不会冲突。

### 2.3 本版不纳入

- 自建模型推理循环或工具执行引擎；
- 通用 DAG、自动多 Agent 分工、任意工作流编辑器；
- 操作系统级进程调度；
- 全新的权限、审批、Attempt 或后端恢复引擎；
- 不受证据约束的自动重试；
- 任意命令冻结、任意外部副作用 exactly-once；
- 应用完全退出后仍保证后台自动执行；
- 没有真实需求就先引入独立数据库进程。

### 2.4 首发场景

推荐围绕用户已有的组件性能测试工作提供两个模式：

1. **分析已有结果**：读取基线与当前结果，计算差异、解释现象、输出报告。
2. **执行测试并分析**：调用已登记的脚本和受支持执行工具，保存真实执行结果后分析。

两者共用任务信息、成果和验收结构。执行模式必须有真实工具回执和资源结束依据；若这些条件尚未接通，先开放分析模式，并明确它不代表本次任务启动过测试。

## 3. 实施前决策：排队能力核实与唯一实现路线

### 3.1 八项能力核实

在隔离的 LyShell userData 和独立 DSH_HOME 中验证，记录应用 SHA、桥版本、实际 Harness 版本、请求、回执和观察结果。可以使用可控模型 fixture 制造协议场景；真实模型任务质量另记。不得修改或重启用户正在使用的共享实例。

| 编号 | 核实问题 | 需要看到的证据 |
| --- | --- | --- |
| C01 | 连续提交超过可运行数量的工作会发生什么 | 明确区分接收排队、busy 拒绝和未知结果 |
| C02 | 等待工作能否被单独定位 | 稳定队列 ID 或稳定请求关联；精确查询 |
| C03 | 等待记录是否持久 | 进程重启后读取到原条目，不靠模型重新记忆 |
| C04 | 等待项能否取消、停止派发 | 取消不启动执行；暂停有真实后端效果 |
| C05 | 并发限制覆盖哪一层 | 同会话、同 owner、全后台或指定资源的实际行为 |
| C06 | 接收后响应丢失能否核对 | 按稳定身份找回原工作；明确保留期限 |
| C07 | 后端重启后会不会继续派发 | 队列暂停状态、后台恢复和执行恢复的真实关系 |
| C08 | 是否支持业务资源约束 | resourceId 或等效机制，以及可核对的释放条件 |

不能把“某次手动演示看起来串行”当成可靠并发控制，也不能把内部 prompt 队列直接命名为业务队列。

### 3.2 路线 N：直接接通原生队列

满足以下条件才选择：

- 等待项持久、可定位、可取消；
- 原生队列覆盖本版要求的并发与暂停行为；
- 同一工作在提交未知时可核对；
- 需要的业务资源规则已被原生支持，或能通过小范围原生扩展可靠实现。

LyShell 保存业务条目和原生队列/任务引用。排队顺序、开始执行、取消等待和实际执行状态均来自后端。

此路线不再建立一份独立的宿主等待队列。若接口尚未暴露但官方已有能力，扩展现有桥和共享协议；同步更新请求校验、宿主、桥、文档和测试。

### 3.3 路线 H：补充宿主待提交队列

当原生队列不能满足必要条件时，采用此路线。

LyShell 保存尚未提交的工作，按额度与资源条件领取，随后调用当前原生 submit。原生接受以后，执行事实仍由原生负责。

宿主仍会根据后端事实保留或释放本层并发占用；“只调度待提交工作”不意味着接受回执后马上释放活动额度。

当前公开工作接口的同会话 busy 行为已经明确。若 C01—C08 没有验证出完整可用的原生路线，路线 H 是本文可直接实施的保守路径；不依赖猜测中的上游能力。[R02][R04]

### 3.4 一项工作只有一个派发负责人

配置保存 queueMode: native 或 host，并固定到每次 Submission。

- 原生已入队的工作，不能再进入宿主待派发列表。
- 宿主交接未知的条目，不能退回普通等待队列。
- 故障时不自动切换路线。
- 切换配置前停止新派发，处理已有等待项和未决交接；现有活动任务继续按原路线跟踪。
- 如果原生队列不能遵守“重启后暂停新派发”的本版约定，就不能仅在前端显示暂停；应补齐原生能力或选择路线 H。

## 5. 最小数据模型与权威来源

### 5.1 三组业务记录

| 记录 | 主要内容 | 权威范围 |
| --- | --- | --- |
| TaskEntry | 标题、目标、模板、输入引用、资源引用、修订版本 | 用户工作定义 |
| Submission | 某次运行的冻结输入、提交身份、交接状态、原生引用 | 用户启动意图与原生执行的关联 |
| ResultBundle | 成果清单、验证结果、业务结论、人工备注 | 已保存成果与验收 |

一次“再次运行”创建新的 Submission。原生 resume 则记录一次续接控制操作，并关联原生返回的新 attempt；不由业务层自行生成原生 attemptId。

TaskEntry、Submission 只是建议名称，可按现有命名规范调整。

### 5.2 最小接口示意

~~~typescript
type QueueMode = 'native' | 'host'
type HandoffState =
  | 'prepared' | 'waiting' | 'sending'
  | 'bound' | 'unknown' | 'rejected' | 'withdrawn'

interface TaskEntry {
  id: string
  revision: number
  title: string
  goal: string
  templateId: string
  templateVersion: number
  inputRefs: string[]
  resourceRefs: string[]
  createdAt: number
  updatedAt: number
}

interface Submission {
  id: string
  taskEntryId: string
  taskRevision: number
  clientOperationId: string
  queueMode: QueueMode
  frozenInputRef: string
  frozenInputHash: string
  acceptanceSpecRef: string
  requestId: string
  idempotencyKey?: string
  handoffState: HandoffState
  nativeQueueRef?: {
    ownerScopeRef: string
    queueId: string
    backendIdentity?: { instanceId: string; instanceEpoch: number }
  }
  nativeExecutionRef?: {
    ownerScopeRef: string
    sessionId: string
    taskId: string
    attemptId?: string
    executionIdentity?: { instanceId: string; instanceEpoch: number }
    executionSessionId?: string
  }
  createdAt: number
}
~~~

说明：

- 以上是宿主内部示意。ownerScopeRef 为内部引用，不进入 renderer DTO。
- sessionId、taskId、attemptId 和 executionIdentity 使用原生返回值。
- nativeQueueRef 只有实际原生接口提供时才使用；不是当前协议中已存在的承诺字段。
- 原生可能先返回排队身份，开始执行后才返回会话/任务身份。两种引用分阶段保存，后续原子补齐关联；不能为满足类型而制造 sessionId 或 taskId。
- 队列身份必须结合所属 scope 与实际后端路由唯一定位；有原生后端身份时原样保存。队列引用与执行引用不能仅按显示名称或顺序猜配。
- prepared 表示输入与提交身份已保存；waiting 仅用于宿主等待队列。
- 路线 N 一旦原生接收，handoffState 为 bound；原生 queued/running 等状态由原生查询展示。
- bound 只表示关联已建立，不能解释为执行成功或可以释放资源。

ResultBundle 至少保存 submissionId、冻结输入摘要、验收规格版本、artifactRefs、检查项、decision、businessOutcome 和人工确认记录。

### 5.3 业务层不保存第二份执行真相

| 信息 | 权威来源 | 业务层允许保存什么 |
| --- | --- | --- |
| 原生 running/completed/failed/cancelled | 原生任务/attempt | 有来源和观测时间的缓存 |
| 审批是否有效 | 当前原生请求 | 历史决定记录和关联引用 |
| 后端是否恢复、是否可 resume | 当前原生能力与恢复状态 | 用户核对说明 |
| 未提交工作是否在等待 | 所选队列负责人 | 路线 H 的持久条目；路线 N 的原生引用 |
| 用户是否接受成果 | 验收规则和人工决定 | 独立验收记录 |
| 资源是否能够释放 | 对应资源的有效证据 | 本层必要占用与证据引用 |

不能让 UI 的“完成”按钮直接修改原生执行状态。

### 5.4 三个维度分别展示

1. **交接/排队**：准备、等待、已交给后端、交接未知。
2. **原生执行与观察**：真实执行状态，加在线/过期/离线等观测信息。
3. **验收**：待检查、通过、未通过、需人工确认。

例如：

- 原生 completed + 验收未通过：执行已经结束，但成果不满足要求。
- 原生 running + 观察 offline：最后确认在运行，目前无法取得进度。
- 原生 completed + 验收通过 + businessOutcome=regression：工作完成，发现性能回退。

## 6. 存储设计：先使用现有基础，保持必要原子性

### 6.1 第一版建议

优先评估现有异步 atomicWriteFile，建立单写者、串行提交的业务 repository。基线已有异步原子替换实现；业务仓储仍需自行提供串行化、版本冲突和操作去重。[R13]

小规模第一版可以采用一个有界元数据清单文件，包含：

- schemaVersion、revision；
- TaskEntry；
- 活动及近期 Submission；
- 路线 H 的等待条目和资源/额度占用；
- 未决控制操作；
- 必要的操作回执；
- 成果索引和验收摘要。

大输入、完整报告、原始结果和日志留在受管文件中，元数据只保存引用与摘要。

### 6.2 必须一次提交的内容

下列操作必须在同一原子快照或同一数据库事务中保存：

| 操作 | 同时保存 |
| --- | --- |
| 创建一次运行 | Submission、冻结输入引用、clientOperationId 回执 |
| 路线 H 领取 | waiting → sending、全部额度/资源保留、提交身份 |
| 保存原生回执 | 原生引用、交接结果、对应操作回执 |
| 撤回未派发工作 | 等待状态、占用处理、操作回执 |
| 人工解除隔离 | 证据、决定、对应占用变化 |
| 保存验收 | 成果快照引用、检查结果、业务结论 |

不能把领取状态写在一个 JSON、资源占用写在另一个 JSON，然后声称两个文件构成事务。

### 6.3 提交确认与去重

- 每个业务变更带 clientOperationId 或 controlOperationId。
- 相同 ID、相同参数返回原结果；相同 ID、不同参数拒绝。
- 使用 expectedRevision 检查并发编辑。
- 原子写提交成功后才更新权威内存快照和通知 UI。
- 无法确定写入是否提交时，repository 进入待核对并暂停后续元数据写入；确认原在途写入已经结束后，重读磁盘清单的 revision、内容摘要和操作回执，再更新内存。不能用旧内存快照继续覆盖可能已提交的新记录。
- 写入成功但响应丢失时，查询原操作记录；不能默认提交失败。
- 序列化一个任务的全部元数据修改，防止旧快照覆盖新记录。
- 第一版不自动淘汰能够触发执行的 clientOperationId、提交关联及其最小去重摘要。删除展示或归档成果仍保留这些依据；达到清单上限时明确拒绝新增工作。以后若要限时淘汰，应先增加可验证的过期操作协议，不能删除记录后把旧 ID 当成新请求。

### 6.4 文件与清单之间的边界

先写入并稳定保存输入/成果文件，再提交清单引用。崩溃时可能留下未登记文件，但不能留下指向尚未写完内容的“成功成果”。

未登记文件先标记为清理候选。清理前排除所有活动、未知交接和验收引用。不得根据一个旧备份把遗漏的执行意图当成从未发生。

从备份恢复或发现数据损坏时，队列保持暂停；先核对原生历史与未确认副作用。不能恢复旧清单后自动派发。

### 6.5 什么时候再使用 SQLite

以下任一条件出现时，明确评估 SQLite：

- 业务数据量使整个清单的序列化或写入影响响应；
- 多个写入者无法合理合并为一个串行 repository；
- 必须跨多份元数据做原子变更；
- 检索、历史规模或频繁变更需要数据库支持；
- 产品明确要求当前文件实现不能提供的耐久性。

选择数据库时再核实实际 Electron 中的驱动、打包和事务行为。SQLite 或独立存储进程不是本版开工前置条件，也不能在运行时失败后静默退回另一种存储。

### 6.6 第一版容量与耐久边界

建议从等待上限 100、元数据清单上限 2 MiB、单个产物 5 MiB、单次成果总量 20 MiB 起步。超过上限明确拒绝或要求显式归档，不能淘汰未知提交和去重依据来继续执行。

这些是建议配置。压测应记录 JSON 序列化时间、写入延迟和界面响应。异步文件 API 不会自动消除大型 JSON 序列化的主线程开销。

现有原子文件实现明确不承诺 Windows 上的完整掉电保证。[R13] 第一版应分别说明进程崩溃恢复与机器掉电耐久性；不能把通过 kill-process 测试解释为所有断电场景都可靠。

## 7. 原生接入与最小提交协议

### 7.1 接入现有服务

业务服务通过依赖注入调用现有 runHarnessWork 和必要只读入口。不要从 renderer 调用桥端口，不在新模块重写原生 HTTP 客户端，不 import HTTP 服务注册入口来获取执行能力。[R07]

宿主需要明确一个稳定、可恢复的业务调用 scope，并复用现有 owner 隔离模式：

- scope 与原生 owner 的关系由主进程控制；
- 不使用临时窗口 ID 充当跨重启执行身份；
- renderer 只能传业务条目 ID，不能选择 owner 或桥地址；
- 复用/新增 scope 时明确与 global、session、Pet 和 Web 的归属边界；
- 旧业务记录只读取它原来有权访问的执行；
- 权限仍在实际派发和原生调用前后复核。

现有 global 原生工作身份可以跨 token 轮换保持，但这并不授权任意调用方直接选取它。[R08] 新业务 scope 的选择应在 W01 中写成明确决策，不靠伪造 global token 完成内部调用。

### 7.2 固定输入与提交身份

用户点击“创建并运行/排队”后：

1. 校验目标、模板、输入引用、资源和完成条件。
2. 保存本次输入快照以及验收规格版本。
3. 为这次用户操作保存 clientOperationId。
4. 创建 Submission，生成并固定 requestId；需要时同时固定 idempotencyKey。
5. 同一用户操作重复到达时返回原 Submission。
6. 用户明确“再次运行”才生成新的 Submission 和提交身份。

草稿编辑只修改 TaskEntry。已经保存的 Submission 继续使用原输入；发现输入错误时撤回尚未派发工作或创建新的执行。

### 7.3 会话创建不能漏掉未知回执

第一版优先在工作真正获准派发时创建所需会话，避免提前为所有等待项占满原生会话额度。

- 不相关目标使用新会话；idle 不代表没有旧上下文。
- 同一目标继续使用已有会话时，明确显示并保存上下文复用选择。
- 创建前保存必要的 sessionCreate 意图和 workspace。
- 收到 new 回执后固定 sessionId 与 workspace。
- new 响应未知时，停止该条目的自动推进；不能循环 new，也不能只凭相同目录或“最新会话”认领。
- 人工选择会话必须验证所属 scope 和关联依据；无法确认的会话创建保持未决。

原生会话数、请求与去重记录有容量上限。[R02] 容量不足明确显示，不轮换 owner、不清空未知历史来绕过限制。

### 7.4 发送顺序

路线 H 的领取与路线 N 的入队前准备都遵守：

1. 保存固定输入与提交身份。
2. 如有本层资源保留，在同一提交中保存。
3. 将 handoffState 保存为 sending，等待存储提交确认。
4. 在真正发送前再次检查生命周期、授权、目标配置指纹和存储健康。
5. 使用保存的原生请求发送一次。
6. 收到确认后保存原生队列/任务/attempt 引用，标记 bound。
7. 不能确定结果时标记 unknown，保留原请求身份并进入核对。

授权范围应当与该次任务和目标关联。最初的 renderer 调用身份只能证明当时的请求来源，不能替代等待数分钟后的权限和配置复核。

### 7.5 回执分类

| 收到的情况 | 处理 |
| --- | --- |
| 明确接收，并带有可验证原生身份 | 保存关联，继续使用原生状态 |
| 有可靠证据表明在派发前拒绝 | 显示原因，按规则等待或结束本次交接 |
| 超时、断线、无法解析、回执归属不明 | unknown，按原身份核对 |
| 原生接收后，业务记录保存失败 | 停止新派发，保留原意图，恢复存储后查原执行 |
| 业务写入失败，尚未发送 | 不调用原生 submit |
| 业务写入成功，返回 UI 失败 | 查原操作回执，不新建一次运行 |

不能仅凭 HTTP 状态码判断“没有执行”。现有服务会在异步调用后再次检查授权，某些拒绝响应可能发生在后端已经接收之后。[R07]

### 7.6 如何找回未知提交

当前公开 state 契约按 sessionId / taskId 查询，并没有承诺一个可任意传入 requestId 的新查询参数。[R03]

实现应使用真实可用路径：

- 已有 taskId：按精确原生绑定查询。
- 回执丢失但已有专属会话：读取该会话的原生任务，核对其中 requestId 与冻结参数关联。
- 现有返回不足以找回：评估增加 owner 内只读的请求查询扩展；将其作为最小协议补充，完整更新校验与测试。
- 查询不到、记录过期或后端离线：保留 unknown，不得解释为从未执行。

原生去重是已有保障，但本版恢复流程优先只读核对。不要换一个 requestId 或 idempotencyKey 来“再试一次”；它会把同一件未知工作变成新执行。

### 7.7 只补交接空隙

业务层的恢复工作是：

- 加载业务记录；
- 找到原生引用；
- 查询未决交接；
- 将用户核对与原生结果关联；
- 恢复成果和验收。

后端冷历史恢复、attempt 生成、原生审批有效性和安全续接继续使用原生机制，不在业务模块另写恢复算法。

跨后端读取时区分“现在提供响应的后端身份”和“该次执行的 executionIdentity”。新的后端可以返回有权威依据的旧执行历史；这种历史只能确认对应旧 attempt，不能结束新的 attempt。

## 8. 排队与受控并发的具体实施

### 8.1 路线 N 的实施要求

1. 把已核实的原生排队 API 接到现有工作服务。
2. 保存原生队列引用，按其稳定身份读取状态。
3. UI 的排队取消、暂停派发均调用真实原生能力。
4. 取原生规定的并发与资源状态，不在前端再计算一套执行顺序。
5. 原生队列暂时不可达时保持状态未知，不将条目转移到宿主队列。
6. 若需要修改桥来开放官方队列，完整审查多任务回合映射、审批路由、取消目标、持久化及旧客户端兼容性。

如果扩展必须重写整个原生任务系统，应重新评估路线 H；“复用原生”不意味着无条件扩大桥改动。

### 8.2 路线 H 的最小队列

只需要一个主进程调度循环和一个持久 repository，不需要额外队列服务器。

建议默认：

| 参数 | 初值 | 含义 |
| --- | --- | --- |
| maxActive | 2 | 本工作台提交范围内的活动/未知交接占用 |
| perSessionActive | 1 | 对齐现有原生接口 |
| pendingLimit | 100 | 本层尚未派发工作数量 |
| priority | 普通 | 首版默认 FIFO；必要时增加低/普通/高 |
| observationInterval | 复用现有轮询；精确补查约 4 秒 | 同一绑定不重入 |
| executionAutoRetry | 0 | 未知或可能有副作用的执行先核对 |
| queueEnabledOnStartup | false | 重启默认暂停新的派发 |

队列处理步骤：

1. 合并入队、额度释放、用户恢复队列等唤醒事件。
2. 任意时刻只允许一个领取过程，防止多个异步回调同时抢额度。
3. 按 enqueueSeq 选择最早可执行条目。
4. 资源阻塞时，可以检查后面的无冲突条目；保留原等待顺序和原因。
5. 在同一原子提交中保留所需额度和全部资源、保存 sending 意图。
6. 完成必要会话准备，发送前再次检查 gate。
7. 调用既有原生 submit；接受后只跟踪原生事实。
8. 根据证据释放相应额度，再唤醒下一轮。

首版不做抢占。如果加入优先级，应增加明确的等待公平规则，不能让低优先级永远没有机会。

### 8.3 活动额度怎么计数

至少计入：

- 已进入 sending，是否接收尚未确认；
- 已接受但未确认结束；
- 正在运行；
- 正在等待审批且原生任务仍活动；
- 取消请求已发出但尚未确认结束。

不计入尚未领取的宿主 waiting 条目。原生终态确认后可以释放后端执行额度，但是否释放测试环境等其他资源，仍看各自证据。

后端暂时无法查询时，使用已持久保存的占用防止超额派发，不以“没看到正在运行”当成空闲。

### 8.4 资源规则先覆盖具体模板

资源记录只需要稳定 resourceId、持有 Submission、占用原因和释放依据，不引入通用租约平台。

例如 A1、A2 使用环境 A，B1 使用环境 B，maxActive=2：

- A1 与 B1 可以并行；
- A2 等待环境 A；
- A1 断线或取消未确认时，A2 仍等待；
- A1 的环境释放被确认后，A2 才能进入派发。

资源名、IP 和连接配置不一定一一对应。同一环境的别名由用户或已有配置明确归一，不能由模型猜测。

### 8.5 释放证据

| 占用类型 | 可以释放的条件 |
| --- | --- |
| 原生活动额度/会话 | 对应原生任务与当前 attempt 已有权威终态，且没有未决控制动作 |
| 每次独立的分析输出目录 | 不作为供其他任务复用的共享环境锁；文件清理另按执行确认与保留策略处理 |
| 共享排他的工作目录 | 受控工具结束证据、实际强制的后台工作限制，或明确人工核对；仅“未发现后台工作”不足以释放 |
| 受管本地脚本 | 受控执行工具给出资源关闭证据 |
| 远端测试环境 | 目标端执行标识/探针确认，或符合流程的人工核对 |
| 人工登记的独占环境 | 保存明确的人工核对与释放记录 |

SSH 通道关闭、网络超时和原生回合结束，不能单独证明远端进程树已停止。既有 CommandExecutionHandle 已把 result 与 resourceClosed 分开，应保留这层区别。[R18]

模板提示“不要启动后台进程”是一项工作约定；只有实际工具权限或执行机制强制时，才能作为强制限制。不能用提示词代替释放证据。

### 8.6 队列恢复

启动后：

1. 读取业务记录和未释放占用。
2. 启动现有只读观察。
3. 标明未决交接与未知资源。
4. 保持新派发暂停。
5. 用户恢复队列后，只派发满足条件的 waiting 条目。

恢复队列不会自动 recover 后端，不自动 resume 旧任务，不批准旧审批，也不消除 unknown 占用。

## 9. 人工介入、取消与续接

### 9.1 复用原生审批

已有 activity 服务会在批准前 fresh read、核对身份、任务和真实选项。[R09] 新界面调用这个入口或抽取并复用同一服务，不复制一份弱化校验。

- 显示实际操作、参数和原生选项；
- 操作信息不完整时保持不可批准，并提供原生工作台定位；
- 不按工具名称猜测某个并行调用；
- 旧审批保留为历史，不在重启后变成可批准项；
- 响应未知时先读原生状态，不自动重复 allowed-once；
- 业务备注保存失败不能让原生审批机制错误地变成自动允许。

### 9.2 区分用户动作

| 动作 | 实际行为 |
| --- | --- |
| 保存任务 | 保存业务定义 |
| 创建并排队 | 创建一次 Submission，按唯一队列路线处理 |
| 暂停派发 | 停止启动新工作，不冻结任意运行命令 |
| 撤回等待任务 | 只取消尚未派发工作，或使用原生队列取消 |
| 请求停止 | 调用原生 cancel，继续等待终态 |
| 补充说明 | 保存人工记录；只有原生明确支持时才送入当前执行 |
| 恢复后端 | 调用 recover，不重发任务 |
| 核对并续接 | 满足原生 resume 条件时提交剩余工作 |
| 再次运行 | 新 Submission，新提交身份 |
| 重新验收 | 重新检查现有成果，不调用 submit |

“打开终端”只是导航，不代表获得独占控制权。需要手工修改环境时，先确认自动执行已停止或处于可靠的可介入边界。

### 9.3 取消的状态表达

- waiting 且未进入交接：原子撤回，不调用 Agent。
- sending/unknown：先核对，不把它当普通未提交条目删除。
- 原生 running：调用 cancel 后显示“已请求停止，等待确认”。
- 原生 accepted/unconfirmed 尚未进入可取消回合：按原生支持处理，不伪造 cancelled。
- 原生确认停止：更新显示；资源依第 8.5 节分别释放。

存储故障时停止新增执行、续接和本层允许操作。已知当前原生任务的停止或拒绝能力可保留，并明确业务审计记录可能未保存；不能为了写一条备注而完全阻断紧急停止。

### 9.4 续接与再次执行

原生 resume 只用于当前协议支持的可恢复任务，用户提供核对后的剩余工作。原生生成的新 attemptId 作为关联保存。[R02][R04]

resume 也是一次新的执行准入，必须检查队列开关、生命周期、额度和全部资源。原有占用仍有效时复核并沿用；已经释放的占用必须重新取得。额度已满时保存待续接意图并等待，不能绕过上限直接调用。

路线 N 必须验证原生限制同样覆盖 resume；路线 H 把续接意图交给同一个调度循环，持久保存 controlOperationId、新 requestId、来源 attempt 与剩余工作摘要。原执行引用保持为历史，直到原生回执确认新关联；续接回执未知时保留占用并查询，不重发。撤回尚未派发的续接只撤回该意图，不改写原任务事实。

已确认 failed/cancelled 的任务，如果不符合 resume 条件，创建有来源关联的新 Submission。后端已经完成但报告缺项，先重采集或复验；需要新的执行工作时，再创建修复 Submission。

人工验收不能改写原生终态。原生失败后补充的人工成果，应记录为后续处理，不能把原执行历史改成成功。

## 10. 成果与验收：从一个模板开始

### 10.1 验收的位置按实际工具能力选择

可采用两种方式：

- Harness 通过受控工具运行确定性的检查脚本，返回可追溯检查结果；
- LyShell 对已经取得的结果文件运行检查函数。

两者都可以。优先复用现有工具链，不为“独立验收”再建一个大型执行服务。

可信度取决于证据来源和关联，不能仅因为文件名叫 verification.json 就认为它是独立证据。

### 10.2 四种证据来源

| 来源 | 能证明什么 | 不能自动证明什么 |
| --- | --- | --- |
| 用户提供的数据 | 本次使用了哪些固定输入 | 测试一定由本次任务执行 |
| 原生受控工具回执 | 某次工具调用及其真实返回 | 未报告的外部进程都已停止 |
| 宿主采集/检查结果 | 实际读取字节、结构与确定性检查 | 模型推测的根因一定正确 |
| Agent 自述/生成文件 | Agent 交付了这段内容 | 内容中的执行声明一定真实 |

对于原生工具证据，记录对应 session/task/attempt 和调用关联。工具结果被截断或现有接口不足以取得完整证据时，读取经许可的原始成果或转人工核对，不在文档中虚构现有 API。

### 10.3 产物最小字段

- artifactId、submissionId；
- 原生执行/调用引用或用户输入来源；
- 保存后的相对位置、格式和字节数；
- 实际读取内容的摘要；
- 采集时间；
- 输入摘要与模板版本；
- 是否稳定、是否完整。

同一成果的后续替换产生新版本。验收绑定当时使用的字节摘要，不跟随一个可以随意变化的绝对路径。

### 10.4 文件处理要求

1. 通过业务 artifactId 定位，renderer 不能要求主进程读取任意路径。
2. 校验实际路径边界、符号链接/junction、文件类型和大小。
3. 有界读取并检查稳定性；文件变化时返回明确错误。
4. 保存受管快照后计算并登记摘要，验收读取同一快照。
5. 不自动访问报告中的外部 URL，不执行附件。
6. Markdown 展示不开放不必要的原始 HTML 或脚本行为。
7. 数据损坏、越界、无权读取不能通过人工“接受”绕过。

成果是文件时不要全部塞进 IPC 或业务清单。列表只返回摘要，内容按需读取。

### 10.5 组件性能模板

#### 输入

- 模式：分析已有结果 / 执行测试并分析；
- 组件和版本；
- 工作目录或已登记测试环境；
- 已有脚本引用、版本与参数（仅执行模式）；
- 基线结果与当前结果，或结果采集约定；
- 指标定义、单位、方向、样本数与工作负载；
- 告警阈值；
- 必需成果与人工确认项。

这些字段在 Submission 中固定。敏感配置保存引用，不复制密码、token 或连接包到提示词和报告。

#### 分析已有结果

1. 复制所选输入为冻结快照。
2. 程序校验 schema、数值、单位、样本和可比条件。
3. 程序计算指标变化。
4. Harness 根据事实表生成解释、可能原因和建议。
5. 组装包含原始事实与分析的报告。
6. 检查输入和输出关联，记录验收。

#### 执行测试并分析

1. 领取任务并确认需要的资源。
2. 通过既有受控执行工具运行已登记脚本。
3. 保存真实执行身份、脚本版本、参数和工具结果。
4. 确认输出完整及资源结束条件。
5. 进入相同的分析和验收流程。

优先使用 Harness 已有受控工具。只有需要由宿主直接运行脚本而原生工具不能满足时，才接现有 CommandService。

当前 CommandService 的实例在 HTTP 服务中组合创建；如果新增调用方必须共享它，应抽出组合入口或注入同一个实例，不能另 new 一个服务造成额度分裂。[R17][R19]

远端执行不具备可靠进程标识/探针时，断线后进入人工核对。这是该执行模式的能力边界，不妨碍分析已有结果模式工作。

#### 验收检查项

| 检查 | 通过条件 |
| --- | --- |
| 输入关联 | 对应本次冻结输入和模板版本 |
| 格式 | 必需字段、有限数值、单位和样本数有效 |
| 可比较性 | 环境、工作负载、指标口径满足约定 |
| 数据计算 | 使用确定性规则计算差异 |
| 执行证据 | 执行模式有真实工具回执；分析模式明确是外部提供结果 |
| 成果 | 原始结果和约定报告完整、可读取 |
| 分析表达 | 事实、推测和待验证事项有清晰区分 |

例如吞吐量 1000 → 900 为下降 10%，延迟 10 ms → 12 ms 为上升 20%。基线为 0、单位不一致或条件不可比时，不能机械计算回归百分比。

### 10.6 验收结果与业务结论

建议分别保存：

- decision：pending / passed / failed / needs-human；
- checks：检查项、结果、证据；
- businessOutcome：normal / regression / not-comparable / not-evaluated；
- reviewer、verifiedAt、verifierVersion。

数据完整、报告符合约定、发现性能下降，可以同时为“验收通过”和“发现性能回退”。不满足自动验证条件时保留待人工确认；人工确认只覆盖验收规格中允许人工判断的部分。

## 11. 工作台交互与 IPC

### 11.1 使用现有界面位置

首版复用侧栏、活动行、通知和已有详情区域，只增加：

- 新建/保存业务任务入口；
- 目标、固定输入和完成条件；
- 队列位置或等待原因；
- 原生执行关联和历史运行切换；
- 成果、检查结果和人工备注。

不另做一套与现有工作台竞争的会话列表、审批中心和浮窗。任务很多时再考虑独立管理页。

### 11.2 业务任务与资源卡片

TaskShelfEntry 目前表达终端、Web、Harness 等资源引用和分类。[R12]

业务 TaskEntry 应通过关联 ID 使用这些资源，不把所有旧卡片自动迁移为“有目标、有验收条件”的业务任务。

- 从已有资源创建任务：先生成草稿，用户确认目标后运行。
- 归档/激活/全部激活：继续只影响分类、导航和原恢复流程。
- 导航到原生执行：使用准确执行引用；不能退回默认选中会话。
- 删除业务展示信息：不能同时隐式取消原生工作或删除去重日志。
- 活动或交接未知记录：不能通过删除卡片解除本层占用。

### 11.3 接口建议

使用可信 applicationIpc 注册业务请求，仍同时更新 handler、校验、preload 和消费端。[R14][R15]

| 业务动作 | 处理位置 |
| --- | --- |
| list/get/save | 业务 repository |
| start | 创建 Submission，交给唯一队列路线 |
| withdraw | 按路线撤回等待工作 |
| setQueueEnabled | 真实队列控制 |
| inspect | 通过原生精确查询，不自动 recover |
| openNative | 现有原生导航 |
| approve/cancel/recover/resume | 复用现有服务和真实能力 |
| addNote | 保存人工说明，不自动注入当前 Agent |
| verify/accept | 成果检查和人工验收 |
| readArtifact/exportArtifact | 经授权读取特定成果 |

公开 DTO 不包含 owner、桥 key、SQL、后台地址或“已授权=true”之类可由 renderer 伪造的字段。

### 11.4 状态文案

| 情况 | 建议文案 |
| --- | --- |
| 宿主等待 | 等待执行 · 前方有可执行任务 |
| 资源冲突 | 等待测试环境 A · 当前由任务 X 使用 |
| 原生 busy 拒绝且未入队 | 后端会话忙，本次尚未排队 |
| 审批 | 等待你的决定 |
| 取消中 | 已请求停止，正在确认执行结果 |
| 提交未知 | 提交结果待核对，暂不重新执行 |
| 离线观察 | 暂时无法获取进度 · 最后确认状态：运行中 |
| 执行完成 | 执行结束 · 等待验收 |
| 验收未过 | 执行已结束 · 成果需要补充 |
| 性能回退 | 任务已完成 · 发现性能回退 |
| 能力不足 | 当前后端不支持此操作，并显示可用处理方式 |

不根据文本日志猜测百分比。后端没有结构化内部步骤时，显示活动记录即可。

### 11.5 观察复用与性能

继续使用现有活动 store 的统一轮询。业务详情需要精确核对时，通过同一宿主读服务合并请求并保持单绑定 single-flight。

活动列表使用摘要，成果和长输出按需读取；新业务 store 不订阅并复制所有终端输出。主进程提交业务记录后通知界面，丢失通知通过重新读取恢复，不依赖无限事件日志。

## 12. 按顺序实施的工程工单

本文使用 W00—W09，避免与上一版 P00—P12 混用。依赖顺序以本节为准，不并行开发两套队列。

### W00：形成能力报告，选定唯一队列路线

**目标**：先确认已有能力，避免重复建设。

**文件范围**：现有工作协议、原生桥、已有测试；新增一份项目实施记录。

**步骤**

1. 固定实际代码与运行版本，阅读第 1 节列出的现有入口。
2. 核对实际后端的 durability、任务身份、审批和恢复能力。
3. 执行 C01—C08；没有实际验证的项目保留 unknown。
4. 对比原生队列路线与宿主队列路线，写清为何选定。
5. 固定并发控制范围、默认上限、资源规则和重启行为。
6. 明确组件性能模板开放的模式及证据来源。
7. 列出必要协议扩展；如果不需要，不改原生协议。
8. 保存已存在测试基线与已知失败，不将文档中的历史测试数字当成当前通过结果。

**交付物**：能力报告、queueMode 决策、首发支持范围。

**完成条件**：团队知道哪些能力直接复用、哪些未暴露、哪些确实缺失；能够说明完整 V1 如何满足五项目标。

### W01：定义最小业务信息与原生引用

**目标**：让工作台能表达用户目标和一次运行，不复制原生执行状态。

**文件范围**：task-workbench.ts、service.ts、harness-adapter.ts 的类型和边界。

**步骤**

1. 定义 TaskEntry、Submission、ResultBundle 和公开 DTO。
2. 固定 clientOperationId、requestId 与原生执行引用之间的关系。
3. 定义交接状态，不在其中再添加原生 running/completed。
4. 定义冻结输入、验收规格与模板版本。
5. 选定稳定的宿主业务 scope，明确其与原有 owner 的关系。
6. 定义权限在保存、入队、派发、控制操作时如何复核。
7. 明确“再次运行”“原生续接”“重新验收”分别产生什么记录。
8. 给出已知/未知/过期快照的展示规则。

**交付物**：共享类型、字段说明、五个关键不变量测试。

**完成条件**：编辑草稿不会改写既有执行；旧原生回执不会被当作新执行；没有第二套原生状态来源。

### W02：建立业务 repository 和输入快照

**目标**：可靠保存新增信息，使用已经存在的存储基础。

**文件范围**：repository.ts；复用 atomic-json.ts。

**步骤**

1. 根据第 6 节实现单写者、串行更新、版本检查和 schema 校验。
2. 建立同一原子快照中的业务条目、提交关联、操作回执；路线 H 同时包含占用。
3. 先保存冻结文件，再写清单引用。
4. 相同 clientOperationId 返回原 Submission。
5. 区分不存在、损坏、不可读和暂时写入失败。
6. 不因损坏创建空清单继续派发；保留原件并提供诊断。
7. 验证写入前后强制终止、写满、重命名失败和响应丢失；不确定时先核对磁盘，防止旧内存回写。
8. 测量清单上限时的序列化与写入延迟。
9. 超出既定规模或保证要求时，按第 6.5 节改选存储；不要在用户运行时静默切换。

**交付物**：可持久保存的业务信息、输入快照、可见存储错误。

**完成条件**：重复运行请求只生成一次业务关联；写入失败不会调用后端；未知交接不会因恢复旧数据而消失。

### W03：接通一次真实提交与原生控制

**目标**：让业务条目关联一个真实原生任务。

**文件范围**：service.ts、harness-adapter.ts、必要 IPC 接口。

**步骤**

1. 注入现有 runHarnessWork 与只读查询入口。
2. 按第 7 节保存创建会话意图、提交身份和发送前记录。
3. 先以单个任务接通，保存真实 sessionId/taskId/attemptId。
4. 复用现有 activity 观察，精确查询只用于补足业务关联。
5. 接通原生审批、取消、recover 和合格 resume；不重写其规则。
6. 验证提交成功但回执丢失，以及回执收到但业务保存失败。
7. 确保错误分类不会把调用后的授权拒绝当成未派发。
8. 不支持的控制动作返回明确限制，不回退到直接终端输入或工具重放。

**交付物**：任务输入—原生执行—状态关联闭环。

**完成条件**：重复打开页面不提交；停止指向正确任务；原生恢复记录可以与业务条目重新关联。

### W04：在现有侧栏和详情中加入业务信息

**目标**：形成可操作的工作台预览版。

**文件范围**：TaskShelf、WorkbenchActivity、已有详情区域、task-workbench store、preload 与校验。

**步骤**

1. 从现有项目/资源入口创建草稿。
2. 表单只收集模板需要的输入、目标和完成条件。
3. 展示保存与运行的区别；原生 busy 拒绝不能显示成排队成功。
4. 将当前业务条目关联到原生执行导航。
5. 在已有审批区域显示真实请求。
6. 添加历史 Submission 切换和人工备注。
7. 归档、激活、全部激活、关闭详情保持既有行为。
8. 增加对应中英文文案，错误时保留用户输入。
9. 列表用摘要和选择器，避免新 store 引发全部终端刷新。

**交付物**：可以组织、运行和观察任务的预览版。

**完成条件**：用户能准确区分自己的工作和原生会话；新增导航没有隐式执行。尚未完成排队时，明确标注预览版能力范围。

### W05：接通成果与首个模板验收

**目标**：任务有明确交付物和完成条件。

**文件范围**：results.ts、component-performance.ts、现有详情中的成果区域。

**步骤**

1. 实现输入和成果的有界读取、路径检查、稳定快照和摘要。
2. 定义性能数据 schema、指标单位、方向与比较条件。
3. 使用固定程序计算差异。
4. 将事实表交给 Harness 分析，保留真实执行关联。
5. 从原生工具回执或合法文件取得证据。
6. 分别显示原生执行状态、验收结果和性能结论。
7. 缺少证据时进入待确认，不调用另一轮模型来“证明自己正确”。
8. 对执行模式接入已有脚本工具；达不到证据要求则不开放该模式。
9. 复验只处理现有成果；新增执行需新的用户操作。

**交付物**：至少一个可用模板、一份可追溯报告、人工验收入口。

**完成条件**：正确数据能通过，缺项/不可比/越界/文件变化能被识别；分析模式不会宣称自己启动过测试。

### W06：实施所选队列路线与并发限制

**目标**：完成真正的排队和受控并发。

**文件范围**：路线 N 的最小桥/适配扩展，或路线 H 的 pending-queue.ts；repository 和 UI 等待原因。

**路线 N 步骤**

1. 接通已核实的原生入队、定位、取消和暂停。
2. 保存原生队列引用。
3. 展示真实排队顺序、活动数与等待原因。
4. 验证原生提供的并发、资源和重启约束。
5. 保持旧客户端的任务、审批和取消语义。

**路线 H 步骤**

1. 实现一个持久等待列表和单个调度 pump。
2. 固定上限、顺序与全部资源领取的原子性。
3. 活动/等待审批/未知交接保留相应额度。
4. 明确 busy 的派发前拒绝与未知结果处理。
5. 原生终态与资源证据分别释放不同占用。
6. 显示等待原因、容量不足和暂停状态。

**两条路线共同要求**

- 一个工作项只有一个派发负责人；
- 不在故障时自动换路线；
- 只宣称实际被控制的范围；
- 同一环境冲突和未知结果不能被手工删除卡片绕过。

**交付物**：可持久排队、并发有上限、冲突可阻止。

**完成条件**：A1/A2 同资源、B1 不同资源的例子成立；真实重启后队列遵守暂停约定；超过额度不会被继续派发。

### W07：补齐交接未知与人工核对

**目标**：业务新增部分不会破坏原生已有的可靠性。

**文件范围**：service.ts、repository.ts、精确查询和详情中的核对操作。

**步骤**

1. 覆盖业务保存、会话创建、submit、回执保存、取消、resume 等故障窗口。
2. 根据原请求身份找回关联，未知时停止该条目自动推进。
3. 使用原生恢复结果，不根据 transcript 的自然语言猜测终态。
4. 显示已确认发生、仍未确认、可能占用的资源和可用操作。
5. 保存人工核对证据与决定。
6. 原生 resume 前再次确认目标、权限、当前 attempt 和剩余工作，并通过与新派发相同的额度/资源准入；已满则等待。
7. 原执行已结束时使用新 Submission；复验不重新执行。
8. 释放资源的动作必须有明确依据，不提供无条件“清空全部锁”。

**交付物**：能处理未知状态的工作台，稳定的交接与核对协议。

**完成条件**：强制中断后不会因自动恢复重复执行；无法证明的事实保持未知，用户能够理解下一步。

### W08：接入生命周期、关闭开关与升级恢复

**目标**：新功能与现有应用的启动、退出和权限撤销一致。

**文件范围**：业务服务组合入口、main/index.ts、现有 lifecycle 接线。

**步骤**

1. 启动先读取业务记录和占用，再恢复只读观察。
2. 新派发默认暂停；路线 N 必须在后端实际实现相同效果。
3. 新派发要求应用处于 running；不利用 cleanup 内部许可启动新任务。
4. 开始退出时同步关闭派发 gate，并使旧异步准备操作失效。
5. 复用现有后端关闭流程，不新增独立重启器或第二次关闭。
6. 在现有总预算内保存最后已确认的业务关联，等待正在进行的 repository 写入。
7. 原生最终状态来不及保存时保留原交接和占用，下次查询原生事实。
8. fatal 路径使用已有最小诊断与退出机制，不在异常状态下继续派发或复杂修复。
9. 关闭业务功能开关先停止新派发；已有原生任务继续可见、可停止，不误停其他 scope。
10. 新业务存储失败只阻止其新增自动工作；原有终端和原生入口按原边界运行，不能被伪造为空历史。

当前生命周期已经提供有界 prepare/revoke/final 流程。[R16] 新回调遵守对应同步/异步契约，不为每个模块追加一份完整退出时限。

**交付物**：启动、退出、故障和关闭功能的明确行为。

**完成条件**：draining 后无新 submit；退出超时可解释；下次启动仍有核对依据；现有产品行为不回退。

### W09：运行验收矩阵并发布完整第一版

**目标**：用实际证据证明五项目标全部完成。

**文件范围**：受影响既有测试、新业务测试、所选路线集成、安装包验证与交付记录。

**步骤**

1. 运行第 13 节 24 项验收，按所选路线执行相关分支。
2. 复用原生并发、去重、审批、恢复和 journal 测试，不重写镜像实现。
3. 对真正新增的业务存储、交接、队列和成果增加测试。
4. 运行 typecheck、架构检查、受影响回归和打包验证。
5. 使用隔离档案与真实受支持 Harness 做 smoke。
6. 人工审批在真实验证中由用户按实际请求决定；fixture 只验证协议。
7. 记录应用、后端、桥、平台、queueMode、执行模式与限制。
8. 所有未通过的目标明确标记，不把预览版改名为完整 V1。
9. 灰度启用，确认资源占用、存储容量和错误提示可诊断后扩大使用。

**交付物**：完整验收记录、支持范围和可用安装包。

**完成条件**：排队、并发、人工介入、故障核对、成果验收均有实际通过证据。

## 14. 发布、演示、升级与回退

### 14.1 两种交付形态

| 形态 | 可以宣称的能力 | 发布要求 |
| --- | --- | --- |
| 工作台预览版 | 业务目标与原生执行关联，现有控制接通，成果与模板验收 | W00—W05 对应验证通过；未完成排队部分明确标注 |
| 完整第一版 | 上述能力，加持久排队、明确范围的并发/资源限制、未知交接核对与启停验证 | W00—W09 和适用验收矩阵通过 |

预览版可以提前提供给用户试用，但不能替代用户要求的完整第一版。

### 14.2 五项目标的发布检查

| 目标 | 必须提供的发布证据 |
| --- | --- |
| 排队 | 一个真实等待项能查询、取消、重启后按约定保留 |
| 受控并发 | 超出额度不启动；同环境冲突被阻止；未知占用不被忽略 |
| 人工介入 | 当前真实审批、取消确认、核对与可用续接流程 |
| 故障核对 | 接收后丢回执不会自动重复；原生事实能重新关联 |
| 结果验收 | 正确成果通过，缺失/错误证据拒绝，结果可追溯 |

不通过的目标必须写明。协议和交接可靠性问题不能作为普通已知问题放行自动派发。

### 14.3 十步演示

1. 选择“分析已有结果”，创建任务 A1。
2. 复制为 A2，登记同一资源；再创建不同资源 B1。
3. 设置并发上限 2，开放队列。
4. 观察 A1/B1 执行，A2 显示等待原因。
5. 在可控 fixture 中制造一个接收后回执丢失，展示精确核对或保持未知。
6. 用真实受支持后端验证当前审批和取消；记录人工决定与实际结果。
7. 展示成果、确定性差异计算和 AI 分析。
8. 使用缺项/不可比数据，展示验收未通过。
9. 重启应用，确认记录可找回、新派发暂停，归档/激活不会执行。
10. 显式恢复队列，只有满足条件的等待项继续；展示“任务完成且发现性能回退”。

fixture 故障实验、真实后端协议和真实模型质量分开记录，不用其中一种代替另外两种。

### 14.4 升级与回退

- 原生 journal 与归属记录保持原路径和语义，不迁移进新业务清单。
- 旧资源卡片保持原有分类；用户主动关联时再创建业务条目。
- 业务 schema 增加版本，升级前保留可恢复备份。
- 不支持的新 schema 明确报错，不创建空库覆盖。
- 回退功能开关只停止新增业务派发，不删除活动、未知或去重记录。
- 旧版本不认识新业务数据时，保留文件并禁用相应功能。
- 切换队列模式前先处置等待和未知交接，禁止把已原生入队的内容重新入队。
- 首发平台通过真实安装包验证；其他平台仍需自己的实际验证，不能仅根据逻辑测试通过就宣称新功能可用。

现有 CI 与打包流程可继续使用，新增验证集中于业务集成和所选队列路线。[R21]

### 14.5 可观测信息

记录足够定位问题的摘要：

- 当前应用/桥/后端版本和 queueMode；
- 业务存储健康、revision、未决操作数量；
- 等待数、活动占用、各等待原因；
- Submission 与原生执行引用；
- 最后确认状态、观察时间、未知原因；
- 资源占用与释放依据；
- 验收规格版本、成果摘要和检查结果。

不记录凭据、桥 key、后台登录 URL、完整环境变量或未经筛选的提示词/工具输出。

| P03/P04 后端适配与单任务闭环 | 保留，明确调用既有服务，不重写执行底座 |
| P05 调度器与通用资源管理 | 先做原生能力决策；只实现选定路线和首发资源规则 |
| P06 审批、取消和人工介入 | 复用原生服务与当前校验，新增业务关联和必要交互 |
| P07 故障恢复 | 复用原生恢复，只补交接空隙和业务核对 |
| P08 生命周期 | 保留必要接线，不新建退出系统 |
| P09 新任务工作台 | 在现有侧栏、活动和详情中增量实现 |
| P10 产物与验收 | 从一个模板和明确证据来源开始 |
| P11/P12 测试与发布 | 复用原生测试，重点验证新增边界；完整五项目标仍需通过 |

不要把两份方案的文件清单和工单相加执行。本版 W00—W09 是后续实施依据。

### 15.2 以后什么时候值得扩大运行时

出现以下实际需求时再扩展：

- 多后端需要统一业务调度；
- 任务必须独立于桌面应用长期运行；
- 多用户或多台机器共享同一任务队列；
- 长期任务依赖、重试策略和定时触发成为核心功能；
- 资源控制需要跨宿主协作；
- 数据规模超过现有元数据仓储能力。

扩展应沿现有业务记录与原生引用接口进行，不重新夺取 Harness 的执行权威。先证明新增需求，随后引入合适存储或运行服务。
