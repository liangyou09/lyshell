# LyShell 小窗口内存优化实施方案与 Rust 边界

日期：2026-10-28。状态：待确认的实施设计，尚未实施本方案中的功能。本文仅授权范围内的文档交付，不代表已获准修改功能、安装 Rust 工具链、增加依赖或迁移数据。

本次文档更新已确认纳入：重启后保存的任务默认进入 Archive；支持单个和全部激活回 Tasks；点击侧栏内容后保持展开，鼠标移出有效区域后再延时收起。确认更新文档不等于授权实施功能。

## 1. 先确定 Rust 用在哪里

结论：保留 Electron、React、xterm 和现有连接层；Rust 优先用于**冷终端历史的分块压缩、解压和索引读取**。浏览器休眠与恢复、贴图缓存策略、实时栏选择仍由 TypeScript/Electron 实现。是否正式接入 Rust，先通过独立基准与总内存测量决定。

| 模块 | Rust 决策 | 具体范围 | 不能据此承诺的效果 |
| --- | --- | --- | --- |
| 冷终端历史压缩与读取 | 首选试点 R1 | 对封存的数据块压缩；按游标、范围读取所需块；限制压缩队列和解压缓存 | 不减少仍驻留在 xterm 中的回滚缓冲，不压缩正在使用的整个网页 |
| 历史索引与搜索 | 后续候选 R2 | 在已经由 Rust 持有的数据上索引、批量搜索，只返回命中范围与片段 | 不因搜索而把全部历史复制回 JS；不能改变已有查询语义 |
| ANSI 清洗与控制字符处理 | 测量后候选 R3 | 仅处理历史查询路径，验证与现有实现的结果一致 | 不替换 xterm 的终端模拟器，不按数据块独立清洗后直接拼接 |
| 图片缩放或编码 | 暂不引入 | 先使用现有 Chromium/Electron 能力、按需采集与缓存预算 | Rust 无法替代网页布局、网页截图与 GPU 合成；编码后仍有解码像素占用 |
| 浏览器闲置、休眠、恢复 | 留在 TypeScript/Electron | 管理 webview 的创建和卸载、导航、恢复元数据、页面保护条件 | 无法通用序列化任意网页的 JS 堆、表单、连接和运行现场 |
| 实时栏、卡片与窗口几何 | 留在 TypeScript/React | 选择唯一实时栏、可视区判断、缩放旧贴图、显示恢复状态 | 不因为用 Rust 就消除 React 重渲染或布局抖动 |
| xterm、IME、PTY、SSH/串口连接 | 本轮不迁移 | 保持现有输入、输出、背压、连接和任务续接机制 | 不通过结束后台任务来降低内存，不重写终端或连接协议 |

Rust 的所有权模型可用于明确数据生命周期，但它本身不保证应用内存下降。需要把原来的常驻副本实际释放，并把原生分配、跨语言副本和临时峰值计入测量。[Rust 所有权说明](https://doc.rust-lang.org/book/ch04-00-understanding-ownership.html)

不把“全量改 Rust”“替换 Electron”“每个小窗启动一个 Rust 进程”作为本方案内容。Windows 系统内存压缩由操作系统管理，本方案不改变系统设置。

## 3. 哪一栏允许实时渲染

### 3.1 唯一实时栏规则

默认将**任务栏**设为实时栏；**Archive/归档栏**默认展示最后贴图。通知栏只展示通知与状态，不参与原生小窗实时渲染。

建议新增侧栏策略 `realtimeView: 'tasks' | 'archive' | 'none'`，这是新设计字段，不是现有 API。允许用户指定归档栏为实时栏，但同一时刻只允许一个栏拥有权限；选择 `none` 时侧栏全部使用静态贴图。

是否允许某个侧栏窗口实时显示，同时满足：

1. 该栏为当前选中栏，并且等于 `realtimeView`。
2. 侧栏已经展开，宿主窗口可见，该窗口内容进入有效可视区。
3. 资源仍存在且不在深度休眠；没有其他生命周期阻止条件。

主工作区正在使用的真实网页或终端不受“唯一侧栏实时栏”限制。它应正常显示；不能因为切换归档栏而暂停主区页面。

| 用户操作 | 预期结果 |
| --- | --- |
| 默认查看任务栏 | 可视小窗允许实时显示；离屏小窗进入闲置判断 |
| 默认切到归档栏 | 任务栏撤销实时与采集申请；归档展示已存贴图，不自动重建网页 |
| 将归档栏指定为实时栏 | 原任务栏权限撤销；只有当前可视且实例存活的归档小窗可实时显示 |
| 单击 Archive 任务卡片 | 该任务移回 Tasks，切到 Tasks 并选中、显示目标；侧栏保持展开，资源按需恢复 |
| 在其他非实时栏点击某任务 | 显示并激活目标；需要主区展示时沿用相应入口，侧栏不因点击自动收起 |
| 查看通知或收起侧栏 | 侧栏所有实时与周期采集申请撤销；后台任务不停止 |

“归档”是任务分类，不是任务终态。归档中仍运行的终端/Agent 继续工作，审批与完成通知正常送达。任务名称、状态、数量可以通过已有事件更新，不需要持续截屏来获取状态。保留此前要求：有多少任务就有多少卡片，不因渲染名额或缓存淘汰而少显示卡片。

### 3.2 统一权限与防竞态

以稳定的任务/资源 ID 管理实时租约；切栏时先撤销旧租约，再授予新租约。小窗注册、截图定时器、后台网页绘制申请共同消费这一个结果，避免只有视觉上换栏、后台两栏仍在截图。

持有实时租约只代表允许展示，不授权关闭、停止或恢复任务。归档栏中的插件、Harness 工作台等不自动套用普通网页卸载规则，继续服从各自所有者的生命周期。

### 3.3 重启后默认归档

LyShell 新进程启动并读入保存的任务后，将启动时这批保存记录统一放入 Archive，包括上次位于 Tasks 的记录；原来已归档的记录保持归档。首屏查看 Archive，保留全部卡片、名称、可取得的最后贴图和真实状态，Tasks 等待本次用户激活。没有可取得贴图时显示占位，不为了生成首屏贴图而加载网页。

此规则只针对保存区任务，不影响未保存任务、其他项目数据或新启动后创建的任务。按启动批次应用一次，初始化重复执行须幂等；用户在本次运行中激活后，普通刷新、组件重挂或列表重读不得再次把它归档。归档分类写入沿用任务仓库的校验和保存规则，写入失败保留记录、显示错误，不把任务丢失或误报为已成功保存。

重启归档不代表任务结束，也不要求先恢复所有资源才能列出卡片：

- 仍存活且可核实的本地终端/Agent，沿现有协议按需附着，不重新执行启动命令。
- 普通网页只读恢复元数据，不批量创建 webview；POST 和其他受保护页面沿用恢复边界。
- SSH 等连接按现有续接范围处理，不新增自动重连或远端任务复活承诺。
- 不能核实的运行状态显示待检查、未知或相应真实状态，不把历史“运行中”冒充当前运行中。

本规则是对 `docs/task-shelf-plan.md` 原有启动展示策略的待实施补充；任务续接、SSH 范围与插件所有权仍沿用原规则。

### 3.4 单个激活与全部激活

“激活”分为**移回 Tasks 的分类操作**和**实际显示/恢复资源**两步。分类变化成功不等于网页已加载或任务已恢复，界面分别显示实际状态。

| 入口 | 分类与显示行为 | 资源恢复规则 |
| --- | --- | --- |
| 单击归档卡片/单个激活 | 只移回该任务；切到 Tasks，选中并定位目标；按现有宽度显示卡片或小窗 | 需要真实显示时复用原实例，否则走该资源已有恢复流程；不自动收起侧栏 |
| Archive 中“全部激活” | 按点击时的归档记录集合全部移回 Tasks，保持稳定次序、数量与 ID；切到 Tasks | 仅当前可视且符合实时权限的小窗按预算恢复，其余保留贴图/占位，禁止同时全部打开或抢焦点 |
| Tasks 中选中卡片 | 保持分类，选中并显示目标 | 已存在实例直接使用；休眠网页先贴图后恢复 |
| 明确的“在主区打开”入口 | 激活并在主区显示目标 | 主区正常交互，侧栏仍不因该点击主动收起，按鼠标移出规则处理 |

“全部激活”不启动新 shell、不重新执行命令、不重新提交 Agent 任务、不重放 POST、不自动回答审批。运行资源是否存在须按原协议核对。静态模式下分类仍能完成，不为实现激活而绕过用户选定的实时栏策略。

批量操作需要独立的 requestId/批次与稳定任务 ID 去重，连点、重读或部分失败不能制造重复卡片或恢复实例。只对点击时那批记录执行；操作期间新归档的记录不被意外带走。失败项保留其记录与真实分类，明确显示失败数量并允许只重试失败项，不显示虚假的全部成功。新恢复的网页使用有界队列，并与截图预算共同验证启动峰值。

### 3.5 点击不收起，鼠标移出后收起

适用于可自动收起的侧栏模式：点击卡片、激活、全部激活、切换分类、操作按钮或输入时，侧栏保持展开；不得在卡片 click、异步恢复完成或打开主区的回调中直接 closePanel。侧栏展开与资源激活使用独立状态。

鼠标离开侧栏及其有效交互区域后，启动约 **350ms** 的延时收起；返回时取消。有效区域包括侧栏本体、通过固定定位显示的真实终端/网页小窗，以及属于侧栏的菜单、弹出层，不能只依靠 aside 的 DOM 包含关系判断。

拖动、尺寸调整、菜单打开或输入焦点仍在侧栏/小窗内部时暂缓收起；这些条件解除后重新核对鼠标位置，再决定是否延时收起。跨 webview 的指针事件需要宿主与 guest 可验证的边界信号配合，不因短暂 mouseleave 就误收。固定模式继续展开；显式关闭按钮与已有关闭快捷键仍可主动关闭。键盘导航不因没有鼠标悬停而突然收起。

用户主动激活使侧栏进入普通“点击后保持展开”状态，而非永久固定；不能为了防止点击收起悄悄把模式改为 fixed。重新显示过程中若鼠标已在侧栏外，先保留本次可见反馈，再按上述延时和保护条件判断。

## 4. 浏览器闲置状态机

以下时间为讨论确认的设计默认值，尚未实测调优或实现。计时以资源在**主区和侧栏均没有实时可见入口**为起点；失去键盘焦点不足以判定闲置。窗口重获可见入口即取消计时。

| 状态 | 条件 | 显示与资源 | 再次打开 |
| --- | --- | --- | --- |
| 活跃 | 任一有效入口正在实时显示 | 原网页正常运行 | 原实例交互 |
| 短暂保活 | 闲置不足 30 秒 | 保留实例；无可视需求不周期采集，保留最后帧 | 直接露出原实例 |
| 贴图保活 | 闲置 30 秒至 5 分钟 | 使用最后贴图，保留实例，撤销不需要的预览申请 | 直接恢复原实例和页面状态，无需导航 |
| 深度休眠 | 闲置超过 5 分钟且保护条件通过 | 保存恢复信息后卸载网页实体，保留卡片和贴图 | 创建新 guest、按最新尺寸加载 |
| 恢复中 | 用户激活已休眠资源 | 贴图保持可见，阻止它接收网页输入；后台加载新 guest | 页面可呈现后替换贴图 |
| 恢复失败 | 离线、加载失败或实例错误 | 保留贴图和真实错误，提供明确重试 | 由用户重试，不无限自动重建 |

贴图保活主要节省采集和绘制开销，保留现场也意味着保留大部分页面内存。不承诺短暂闲置期间网页自身完全停止活动；实时状态、长连接和网站逻辑仍可能变化。

### 4.1 自动深度休眠的范围

首版只覆盖用户允许、可通过普通 GET 地址重新访问的普通网页。以下情况阻止深度休眠：

- 用户设置“始终保持运行”；DevTools 或页面检查正在进行。
- 播放、通话、录屏、上传、文件交互或其他依赖页面继续运行的活动。
- 检测到未保存编辑、未提交表单、待确认关闭提示，或页面仍在导航/提交。
- POST 首航与提交结果页、一次性令牌地址等不能确认安全重开的页面。
- 插件拥有的页面、Harness 工作台、特殊内部页或由其他资源所有者管理的页面。
- 保护状态未知。普通跨站页面的状态不能可靠穷举，**未知按保活处理**；不能将“没检测到”视为“没有”。

保护判断失败只影响网页休眠，不影响卡片停止截图。资源紧张时也不能绕过这些保护条件静默卸载。

### 4.2 保存与恢复边界

恢复元数据至少包括稳定 taskId、最终导航 URL、原 partition、原 zoom、可安全获取的滚动位置、版本和状态。沿用当前 session/partition，不在恢复记录复制 Cookie、密码或 POST 正文。

Cookie 与浏览器存储可继续沿用，但登录是否仍有效由网站决定；不能保证 sessionStorage、网页 JS 对象、WebSocket、内存内令牌或临时表单恢复。滚动位置尽力恢复；SPA 页面高度尚未稳定时不能无限重试。浏览历史恢复需另做当前 Electron 版本能力验证；首版若只支持当前 URL，必须明确记录限制，不把地址列表冒充完整历史栈。

贴图不是页面快照。禁止重放 POST、自动提交表单、伪造已恢复的工作台会话。自动休眠前必须满足可恢复条件，保存失败则保持原实例。

优先保留“卸载前保存成功、旧实例已释放、新实例准备好”的可核实状态。`dom-ready` 或 `did-finish-load` 不能单独证明实际画面已呈现；结合布局有效、可截取帧与加载事件验证切换时机，失败时留在贴图/重试状态。[Electron 截图 API](https://www.electronjs.org/docs/latest/api/web-contents#contentscapturepagerect-opts)

使用 `taskId + generation` 标识一次实例和恢复请求；关闭、导航、换实例后旧截图和旧加载回调不得回写，也不得重建已关闭的卡片。快速连续打开合并为一次恢复。

不要依靠 setTimeout 恰好执行来判定档位：保存闲置起点和截止条件，回调执行时重新核对 generation、可见入口和保护状态。系统锁屏、休眠/唤醒后先重新取状态；不同平台时钟跨系统休眠的行为需验证，不能仅凭一次迟到计时器批量卸载网页。持续改宽时延后销毁，待交互结束重新判定，避免拖动与回收互相打断。

## 5. 贴图、宽度变化与缓存预算

### 5.1 调宽后的显示

1. 拖动时保持内容框 16:9，以 `contain` 等比例显示已有贴图；不拉伸、不裁掉内容。旧网页画面比例不同可留边。
2. 同一帧合并几何更新；不在每次 pointermove 编码、截图或重新加载网页。
3. 拖动结束或尺寸稳定约 200ms 后，只有存活且获得采集许可的网页才按最新尺寸布局、重新采集；同一资源最多一个在途请求。
4. 已休眠网页仅缩放旧贴图，不因尺寸、DPI 或卡片进入视口而唤醒；真正激活时按最新内容区尺寸创建 guest。
5. 新图准备好后替换旧图；只保留最新有效版本。旧宽度的异步请求完成时不得覆盖新宽度贴图。

放大期间可能短暂模糊。静态贴图不会重新排版，真实网页恢复后才根据新视口布局。缩略图显示不得修改 PTY 行列；真实终端小窗的尺寸同步继续服从独立的终端 resize 调度。

### 5.2 缓存模型

以 `resourceId + instanceGeneration + navigationGeneration` 为身份，共用最近帧。宽度是更新参数，不作为无限增长的缓存键。每份资源只有一个已提交帧，更新时可临时持有旧、新两帧，但必须计入峰值预算。

建议初始实验预算如下，全部为**待基准验证的参数，不是已实现或保证值**：

| 项目 | 初始实验值/规则 |
| --- | --- |
| 网页预览最长尺寸 | 先维持当前最大 960×600；实际按显示尺寸和受限 DPR 生成 |
| 解码图片与 Canvas 合计 | 64MiB 软预算；含可见帧、过渡旧帧和终端预览 |
| 编码图片驻留 | 16MiB 软预算；与解码占用分开记账 |
| 采集并发 | 全侧栏最多 1 个在途网页截图，先保证可见与被激活资源 |
| 持久化贴图 | 首版默认不新增落盘；后续可选有界磁盘缓存，需单独确认 |

960×600 的 RGBA 像素约为 2.2MiB，这不包含编码串、原始 capturePage 大图、GPU 副本及解码器开销。当前代码先完整截图再缩小，峰值可能高于最终贴图；开发时验证可用的裁切/尺寸控制，不能只限制最终图就声称峰值有界。

优先保存可见与最近使用帧，离屏项释放解码显示资源；缓存紧张时可降低旧帧分辨率、淘汰编码副本，保留卡片和元数据。**“所有任务都有卡片”必须满足；“无限任务各保留高清贴图”与有限内存预算不能同时保证。**无图项显示标题、状态和占位，禁止为补图唤醒休眠网页。若产品要求所有最后贴图都保留，再另行确认有容量上限的磁盘缓存及淘汰规则。

首轮先在现有 DataURL 路径上做所有权和数量限制。Blob/Object URL 作为后续实验：先核对 CSP、IPC 传输和生命周期，在替换、关闭、淘汰时 revoke，不能直接添加宽泛 CSP 权限。Canvas 释放后重置像素尺寸；清理组件 state、帧缓存、注册表和在途 Promise 引用，不能只隐藏 `<img>`。

网页采集是最后画面获取机制，不是高帧率视频传输。静态栏不周期重采样；实时原生小窗直接显示网页，不需要截图模拟交互。

## 6. Rust 原型的具体实现边界

### 6.1 第一个原型：冷块编解码和索引

先用固定日志 fixture 建立独立原型，不接生产终端热路径。对比当前 TS、Node 已有异步压缩能力、Rust 实现的**总成本**，算法候选为低延迟 LZ4 与 Zstandard；选择依据是小块吞吐、压缩率、临时内存和解压延迟的测量，不先承诺某种算法获胜。

待原型通过并获得实施确认后，首个生产候选是已封存的历史数据。不要为了“可压缩”额外扩大日志保留量。活跃查询尾部仍保持现有有界存储，旧块转冷后释放原副本；若数据必须同时永久驻留 JS 和 Rust，取消这一迁移。

建议原型接口（新设计，不是现有导出）：

| 操作 | 输入/输出与约束 |
| --- | --- |
| `openStore` | sessionId、预算、格式版本；返回有所有权的句柄 |
| `appendSealedBlock` | 序号、起始码元游标、码元数、UTF-16LE 数据；批量异步提交 |
| `readRange` | 码元游标与上限；只解压相交块，返回数据、下一游标和截断标记 |
| `trimBefore` | 淘汰指定游标之前的数据，同时清理索引与解压缓存 |
| `stats` | 原始等价量、压缩字节、索引、缓存、排队与在途字节 |
| `closeStore` | 幂等取消任务、释放句柄；后续旧请求不得回写 |

压缩块从 64KiB 原始字节开始实验；热尾、块数、队列、解压结果和全局预算全部有限。并发先设 1；数据不可压缩或压缩收益不足时保留未压缩块，不能为了压缩增加无界副本。达到预算先按既有历史上限淘汰，不能阻塞或丢弃尚未送往终端的实时数据。

### 6.2 必须保留的字符串与查询语义

- 现有缓冲容量和游标以 **UTF-16 码元**计，不是字节、Unicode 字符或 UTF-8 偏移。
- 现实现允许截断后留下孤立代理项。Rust 的 `String` 不能直接表示任意这类序列；兼容原型用原始 UTF-16LE 字节或 `u16`，不得经过有损 UTF-8 转换。
- 若以后改用 UTF-8，须提供可逆编码、码元映射和显式格式版本；不能假定 UTF-8 总比 V8 字符串省内存。
- 保留游标、clear 后代际、trim、truncated、原始/清洗查询及行数语义。
- ANSI 序列、回车覆盖、退格和代理对可能跨块。压缩独立不等于文本清洗可独立，R3 必须保留跨边界解析语义。

`OutputBuffer.getRecentLines/getOutputSince` 当前为同步查询，`sendAndWait` 也使用现有游标。不能把有耗时的冷块解压直接塞入同步方法。迁移前梳理调用方并明确异步适配；首版不改这些同步热查询，也不修改 MCP 的既有返回语义。更不能把“对主进程历史查询可用”当作“xterm 可以按需读取压缩回滚历史”：后者是独立的大范围终端设计，本轮不做。

### 6.3 接入方式与线程

首选评估 **Rust Node-API addon + 专用 Node Worker**。addon 不在 renderer 加载，renderer 继续经 preload/受校验 IPC 访问；压缩和较大解压在 Worker 中执行，主进程只做有界调度。只创建应用级共享 Worker，不为每个小窗各启运行时。

Node-API 提供 ABI 稳定接口，但仍需按 Electron 实际内嵌 Node-API 版本及 OS/CPU 构建验证，不能把开发机 Node 的最新版功能当作 Electron 已支持。原生依赖和超出 Node-API 的调用不自动获得同等兼容性。[Node-API 文档](https://nodejs.org/api/n-api.html)

Worker 不提供进程崩溃隔离。若崩溃隔离成为需求，再比较“utilityProcess 加载 addon”和“独立 Rust 可执行程序”；utilityProcess 本身是 Node 入口，不是直接运行 Rust 二进制的接口。新增进程的常驻开销和 IPC 副本必须计入。[Electron utilityProcess 文档](https://www.electronjs.org/docs/latest/api/utility-process)

所有边界规定字节所有权：提交后哪一方释放、是否复制、是否转移；写队列有上限；只返回请求范围，不返回整库。未证明所有权和 API 支持前不宣称零拷贝，不把同一缓冲在多侧的引用计成多个独立数据集。

不使用 WASM 作为首选内存方案：先证明独立线性内存和 JS 交换副本的成本；不因部署方便就假定它更省内存。

### 6.4 失败、格式与回退

压缩块包含格式/算法版本、原始长度、码元范围与校验信息；限制解压尺寸和比率，遇到损坏报告明确错误，不无限重试或分配。句柄释放和队列取消幂等；关闭资源后拒绝迟到结果。

原型保持 TS 后端可选。原生模块加载失败时，新数据走 TS 有界存储；已经只有压缩副本的历史必须有兼容解码或先迁回再切换，不能仅改一个开关就宣称无损回退。若尚无可靠历史迁移/解码，生产迁移不放行。仅数据处理 Worker 失败不得终止 PTY、自动重启 shell 或重新执行 Agent 任务。

先验证 Windows x64 的实际 Electron 打包、加载和卸载；支持的其他平台各自验证。仅新增模块被配置进构建/打包，不改变 renderer 沙箱、安全设置或现有 native 模块 ABI 处理。

## 8. 测量、Rust 采用门槛与测试矩阵

### 8.1 固定测量方法

- 在隔离用户档案与本地 fixture 中测量，不操作用户真实表单、账号或活跃任务。记录应用版本、OS、内存、屏幕刷新率/DPR、页面数、终端数、输出量、历史与缓存预算。
- 场景覆盖 1/10/30 个网页、20/100 张卡片、1/10/30 个终端，以及文本、ANSI 密集、中文/emoji、高熵内容。分别报告时间与内存，不能把 gzip 易压缩 fixture 当作所有真实网页。
- 采样覆盖预热后稳态、刚截图峰值、进入贴图保活、5 分钟后深睡、恢复与关闭；至少重复 3 次，报告中位数与范围。
- 额外对比“重启后静态归档”“单个激活”“全部激活但仅可视恢复”的首屏时间与内存峰值；验证全部激活没有变成全量网页预加载。
- Electron 主进程、renderer、guest、GPU/utility/native 进程按 PID 去重；shared process 无法精确归因到单个网页，报告进程组增量。分别列工作集、私有内存、JS heap、external/ArrayBuffer、Rust 自统计，不把相互包含的指标简单相加。
- shell/Agent 子进程单列并报告应用相关总量；不把外部进程占用算成小窗渲染内存，也不能在总量里隐去新增 Worker/原生进程成本。
- 隐藏/卸载后内存回收可能延迟，区分引用释放证据、分配器保留和系统工作集变化。不通过频繁强制 GC、清空工作集制造节省曲线。
- 同时记录贴图首显与真正可交互耗时的 p50/p95、长任务和实际帧时间。rAF 调用频率不是实际呈现帧率；帧同步优化结果由另一个任务验证并合并测量。

### 8.2 Rust 放行条件

以下为建议门槛，待基线后确认；目前没有测量结果，也不承诺固定节省比例。

1. 数据一致性全部通过，历史游标与终端/MCP 行为不变；所有队列、缓存和解压输出有界。
2. 相同数据集、保留策略和工作负载下，相比优化后的 TS/Node 压缩对照，应用相关总私有内存有稳定、超过重复测量波动的下降；提供绝对 MiB 与相对值。
3. 不是仅 JS heap 下降、native/external 或新增进程上升；同时验证处理与切换时的峰值。
4. 冷历史读取、输入响应与界面长任务没有不可接受的退化；小数据场景的额外 Worker、模块体积和维护成本也记录。
5. 发布平台能可靠加载，失败可诊断，压缩历史的兼容与回退路径已验证。

如果收益只来自算法和缓存策略，现有 Node 方案已达到要求，就保留 TS/Node，不为使用 Rust 额外引入运行时边界。

| 场景 | 必须验证 |

## 9. 实施前需要确认的具体选择
